# 세션 0 실습 랩 — 환경 구축과 첫 실행

> **선행 조건**: 없음. C 언어 기초만 있으면 됩니다.
> **소요 시간**: 약 50분
> **목표**: `cuda_memtest`를 직접 빌드·실행하고, 이 도구가 무엇을 하는지 감을 잡습니다.
> 한글 용어 옆의 (영어)는 원어 표기입니다.

## 이번 세션의 목적

앞으로 5회에 걸쳐 우리는 **실제로 동작하는 GPU 프로그램**(`cuda_memtest`)을 교재로 CUDA를 배웁니다.
세션 0에서는 먼저 **환경을 갖추고, 한 번 실행해 보는 것**이 전부입니다. 코드는 아직 몰라도 됩니다.
"GPU가 실제로 일한다"를 눈으로 확인하는 것이 목표입니다.

## Exercise 0 — 내 환경 점검

**① 목표**: CUDA를 빌드·실행할 준비가 됐는지 확인한다.

**② 명령**:

```bash
nvidia-smi          # GPU가 보이는가? 이름·메모리·드라이버 버전 확인
nvcc --version      # CUDA 컴파일러가 있는가?
cmake --version     # CMake 3.x 이상인가?
```

**③ 관찰**:
- `nvidia-smi` 출력에서 본인 GPU 이름과 총 메모리(예: 24 GB)를 적어두세요.
- CUDA 버전(예: 12.x)과 드라이버 버전을 확인하세요.

**④ GPU가 없다면?**
- **Google Colab**: 런타임 → 런타임 유형 변경 → GPU 선택 (무료로 CUDA 환경 제공)
- 또는 클라우드 GPU 인스턴스 사용
- 강사는 미리 캡처한 실행 로그로 결과를 대신 보여줄 수 있습니다.

> 본인 GPU의 아키텍처 번호(`sm_XX`)는 https://developer.nvidia.com/cuda-gpus 에서 확인합니다.
> 예: T4 → 75, RTX 30 시리즈 → 86, RTX 40 시리즈 → 89, A100 → 80.

## Exercise 1 — 빌드하기

**① 목표**: 소스에서 `cuda_memtest` 실행 파일을 만든다.

**② 명령**:

```bash
mkdir -p build && cd build
# 본인 GPU 아키텍처로 교체 (예: 86)
cmake -DCMAKE_CUDA_ARCHITECTURES=86 ..
make -j
```

**③ 관찰**:
- `cmake` 단계에서 `CUDAToolkit`, `Threads`를 찾았다는 메시지가 나오는지 확인.
- `make` 완료 후 `build/` 안에 `cuda_memtest` 실행 파일이 생겼는지 확인(`ls -la cuda_memtest`).

**④ AMD GPU라면?** 이 도구는 HIP 백엔드도 지원합니다.

```bash
cmake -DCUDA_MEMTEST_BACKEND=hip -DGPU_TARGETS=gfx90a ..
make -j
```

> CMake 옵션 `CUDA_MEMTEST_BACKEND`(cuda/hip)로 백엔드를 고릅니다(`CMakeLists.txt:22`).
> 하나의 소스가 두 GPU 벤더 모두를 지원하는 비결은 세션 5에서 배웁니다.

**⑤ 생각해보기**: 왜 GPU 아키텍처 번호(`sm_XX`)를 빌드할 때 지정해야 할까? (GPU 세대마다 기계어가 달라서)

## Exercise 2 — 어떤 테스트가 있는지 보기

**① 목표**: 이 도구가 제공하는 11개 메모리 테스트를 확인한다.

**② 명령**:

```bash
./cuda_memtest --list_tests
```

**③ 관찰**: 다음과 같은 목록이 나옵니다.

```
Test0  [Walking 1 bit]                주소 배선 검사
Test1  [Own address test]             주소 검사
Test2  [Moving inversions, ones&zeros]
...
Test9  [Bit fade test]  ==disabled by default==   (3시간 소요, 기본 비활성)
Test10 [Memory stress test]           스트레스·소프트 오류
```

**④ 생각해보기**: Test 9(bit fade)는 왜 기본적으로 꺼져 있을까? (한 번에 약 3시간 걸리는 데이터 보존 검사)

## Exercise 3 — 첫 실행 (빠른 스트레스 테스트)

**① 목표**: GPU 메모리 검사를 실제로 돌려본다.

**② 명령**:

```bash
# 빠른 상태 점검: 스트레스 테스트(Test 10)를 짧게 실행
./cuda_memtest --stress --num_iterations 100 --num_passes 1
```

`--stress`는 `--disable_all --enable_test 10 --exit_on_error`와 같습니다(README 참고).

**③ 관찰**:
- 로그 접두사 `[시간][호스트명][GPU번호]` 형식을 확인.
- "Allocated N MB", "Test10 ... finished in X seconds" 메시지 확인.
- **오류가 없으면** 정상 종료합니다(건강한 GPU).

**④ 또 다른 실행 — 무한 반복 기본 동작**:

```bash
# 옵션 없이 실행하면 모든 테스트를 무한 반복 (Ctrl+C로 중단)
./cuda_memtest --num_passes 1     # 1회만 돌고 종료하도록 제한
```

**⑤ 생각해보기**: 왜 이런 도구는 기본이 "무한 반복"일까? (소프트 오류는 드물게 발생 → 오래 돌려야 잡힘.
자세한 이유는 `doc/`의 논문에서, 세션들에서 조금씩 배웁니다.)

## Exercise 4 — sanity_check 스크립트 살펴보기

**① 목표**: 실전에서 GPU 건강을 빠르게 점검하는 방법을 본다.

**② 명령**:

```bash
cat ../sanity_check.sh          # 스크립트 내용 확인
# (빌드 디렉터리에 바이너리가 있으면) 직접 실행도 가능
```

스크립트의 핵심은 한 줄입니다:

```bash
cuda_memtest --stress --num_passes 1 --num_iterations 100 [--device N]
```

**③ 관찰**: 이 스크립트는 `--device` 인자로 특정 GPU만, 인자가 없으면 모든 GPU를 점검합니다.

**④ 생각해보기**: 데이터센터에서 수백 대의 GPU를 어떻게 관리할까? 이런 간단한 스크립트를 주기적으로
돌려 불량 GPU를 걸러냅니다. 실제 이 도구는 NCSA의 대규모 GPU 클러스터 운영에서 나왔습니다(`doc/` 논문).
